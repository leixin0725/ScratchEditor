# ScratchEditor Constitution

## Core Principles

### I. 用户环境安全与开发隔离（不可妥协）
开发、验证和自动化操作不得破坏用户环境。除非用户明确要求部署，否则不得修改 AHK 文件、
剪贴板、用户配置或 `%LOCALAPPDATA%\ScratchEditor\CodexEditor`、`AhkEditor` 稳定副本。
开发迭代必须使用 `editing` 或 `window-ui` preset，并传入 `-SkipLocalInstall`；测试必须使用
隔离的服务器名、进程和配置。获准部署时必须先确认精确目标，并在结果中说明影响和恢复方式。
这些规则用于保护常驻编辑器、用户数据和外部工具集成不受开发活动干扰。

### II. 架构与产品边界必须稳定
项目必须保持 Windows 原生 Qt 6 / C++20 / QML 架构：编辑核心和系统集成归属 `src/`，界面归属
`qml/`。生产 IPC 只能开放白名单命令；测试命令只能用于 `--test-mode` 隔离实例。外部编辑必须
使用 `--wait <path>` 文件模式，以 UTF-8 读写并绕过剪贴板、常驻 IPC 和单实例转发。项目不得提供
Markdown 预览，也不得引入 WebEngine、WebView 或其他浏览器内核。主题与窗口配置必须继续使用
既有单一事实来源，避免配置分叉和运行模式间的隐式耦合。

### III. 文本正确性与线性性能
所有文本坐标必须使用 Qt UTF-16 code-unit 索引，不得与 UTF-8 字节偏移混用。编辑核心的每次操作
必须保持线性复杂度，每次编辑最多进行一次全文读取和一次分析；实现必须先收集插入点，再按倒序
写入。候选循环中不得重复调用 `toPlainText()` 或重复扫描全文。涉及 Unicode、空文档、文档边界、
混合换行和重叠编辑范围时必须有明确行为和验证，以防止坐标漂移、越界或非预期的二次修改。

### IV. 测试先行与证据闭环（不可妥协）
行为修复和新增功能必须先添加能够稳定失败的测试，再实施代码变更。关键边界必须使用独立 check 名，
失败输出必须包含 actual 与 expected 细节。不得通过删除、跳过或放宽有效断言掩盖回归；偶发超时最多
重跑一次，并必须单独记录。验证范围必须与风险匹配，使用 `tests/README.md` 定义的入口和顺序；需要
阶段证据时，最终结果必须保存到既有基线位置。任何未执行或失败的验证都必须在交付报告中明确说明。

### V. 最小、可维护且有文档依据的变更
实现必须保持需求范围内的最小变更，遵循现有命名、格式和代码风格，并优先选择简单、解耦、可维护的
设计。不得为未确认的未来需求堆砌抽象；不得无故改写既有注释，只能添加解释必要约束的注释。所有含
中文的项目文本必须使用 UTF-8（无 BOM）。重要改动完成后必须检查 `README.md`、`tests/README.md`
和 `docs/README.md` 是否需要同步；持续更新的项目细节只写入根 `README.md`，完结功能资料移入
`docs/archive/`，并维护文档索引。

## Additional Constraints

- 支持的基础工具链为 Qt 6.10.2、C++20、MinGW 13.1、CMake 3.25+ 和 Ninja；工具链位于
  `.tools/Qt` 且不得进入 Git。
- 单实例常驻窗口、生产 IPC 白名单、外部文件模式和集中配置的既有兼容契约不得在没有迁移方案与
  用户批准的情况下破坏。
- `quit` 仅是 `--test-mode` IPC 命令，不是命令行参数；任何脚本不得执行
  `ScratchEditor.exe --quit`。
- 与外部 API、SDK 或在线服务有关的设计和实现必须先联网核对当前官方文档，并在变更说明中记录
  采用的真实接口状态。
- 沙箱内不得写入 `.git`；暂存、提交和其他修改 `.git` 的操作必须使用获准的沙箱外权限。

## Development Workflow

1. 开始改动前必须阅读与任务相关的正式文档、架构和现有实现，并记录无法从仓库确定的需求歧义。
2. 新对话中的项目改动必须先向用户提交修改计划并获得批准；高影响歧义必须继续确认，不得擅自选取
   会改变产品行为或范围的方案。
3. 实现必须遵循测试先行：建立稳定失败的回归用例，完成最小实现，再执行与风险对应的隔离验证。
4. 完整回归必须遵循 `tests/README.md` 的 release、system、外部编辑器、editing、window-ui、AHK、
   perf 顺序；普通开发验证不得借完整回归之名隐式部署稳定副本。
5. 交付前必须审查 diff、测试结果、边界情况和文档影响。若构建成功但未部署，必须报告可测试的
   可执行文件位置；只有用户要求时才执行提交或部署。
6. Git 提交信息必须使用简体中文，遵循社区通用的类型与主题格式，并准确描述变更范围。

## Governance

本宪章定义跨功能、长期有效的项目规则；根 `README.md` 是持续更新的架构、功能和操作细节的单一正式
来源。若两者冲突，涉及安全、产品边界、质量门禁和治理流程时以本宪章为准，并必须在同一变更中修正
相关文档。

宪章修订必须提交书面理由、影响范围和 Sync Impact Report，并在用户批准后生效。删除原则、放宽
不可妥协约束或重新定义既有治理含义属于 MAJOR 版本；新增原则、章节或实质扩展约束属于 MINOR 版本；
澄清、措辞和不改变含义的修正属于 PATCH 版本。破坏现有工作流或兼容契约的修订还必须提供迁移方案。

所有规格、计划、任务清单、代码审查和交付报告都必须核对本宪章。任何例外必须在实施前获得用户明确
批准，并记录理由、范围、风险和恢复方式。重要变更完成后必须复查正式文档与归档索引的一致性。
