# 核心代码重构调查报告（2026-11-12）

## 已确定的维护顺序

以下顺序用于约束后续重构范围；每一项均应独立实施和回归，不做跨层大规模重写：

1. **拆分 `EditorController` 职责**：剪贴板访问、历史加载/捕获/持久化和错误聚合已收敛到
   `ClipboardHistoryCoordinator`；下一步隔离测试 IPC 和性能基准设施。继续保持现有 QML 属性、
   IPC JSON、ready/test 门禁及窗口生命周期语义不变。
2. **按垂直能力治理 `EditorCommandRegistry`**：依次评估输入自动滚动、选区拖动和纯文本变换的
   提取，不做一次性重写；继续遵守 Qt UTF-16 索引、单次全文读取/分析及线性复杂度约束。
3. **拆分 editing 验收代码**：按编辑领域拆分 `tests/editing_main.cpp`，共享 IPC 客户端与断言工具，
   但保留现有测试可执行文件、脚本入口、独立 check 名和机器可读产物格式。

只有当前一项完成隔离构建与对应完整回归后，才开始下一项；纯粹移动代码时不得顺带改变产品行为。

8 月建议中的 QML 面板拆分已完成。若统一 toggleTask 与 toggleCheckbox，须先确认有序项与引用前缀的移除语义，并补对应测试。

## 结论

项目需要局部重构，不需要整体改架构。优先治理已有职责耦合和规则分歧，不按文件长度机械拆分，也不引入通用编辑框架、插件体系或完整 Markdown AST。

| 候选项 | 主要收益 | 实施风险 | 建议 |
|---|---|---|---|
| 隔离控制器中的测试 IPC、采样和基准设施 | 缩小生产控制器职责，降低验收扩展对生产代码的影响 | 相对较低，但必须保持协议和异步时序 | 第一项实施 |
| 收敛编辑区滚动状态所有权 | 降低输入、查找、标题导航和拖动之间的交叉回归风险 | 高 | 长期业务收益最大，按垂直能力推进 |
| 统一围栏识别规则 | 消除高亮、折叠和编辑保护对同一文本的判断分歧 | 中，涉及可见行为变化 | 独立确认语法边界并修复 |
| 提取列表文本变换算法 | 降低编号、续行、缩进等规则的修改与验证成本 | 中 | 第二梯队 |
| 按领域拆分 editing 验收代码 | 改善定位、阅读和维护效率 | 较低，但需避免改变用例状态依赖 | 按现有维护路线后续推进 |

## 1. 优先隔离 EditorController 的测试设施

### 代码证据

- `src/editorcontroller.cpp:1175` 的 `buildCommandHandlers()` 超过千行，同时注册生产窗口命令、测试输入注入、测试控制和性能基准。
- `dispatchCommand()`（1131 行）统一处理 ready/test 门禁，测试命令与生产命令共享分发基础。
- `captureEditorRenderSample()`（2347 行）、`captureStatusPanelBorderSample()`（2428 行）及 `runLargeDocumentBenchmark()`（3922 行）等测试设施与窗口生命周期处于同一类。
- `statusObject()`（3556 行）同时组织生产状态和大量测试诊断字段。

### 为什么值得重构

新增验收场景会持续修改应用主控制器，即便产品行为没有变化。阅读生产生命周期时也需要绕过测试设施。这里的职责边界已经明确，拆分收益不依赖未来功能假设。

现有门禁已经存在；本建议不意味着发现了测试命令可被生产实例调用的漏洞。

### 最小实施边界

提取一个具体的测试支持对象，承担测试命令注册、采样、基准状态和测试诊断组织。控制器保留生产分发、门禁和窗口生命周期。只提供测试所需的窄接口，不为迁移方便公开全部私有成员，不引入通用 IPC 框架。

不能仅把成员函数移动到另一个 `.cpp` 就视为职责隔离完成；状态归属与访问边界也应明确。

### 必须保持的行为

保持 IPC JSON、requestId/noReply、ready/test 门禁、异步回复、断连与窗口退出时的清理语义。验证应覆盖生产实例拒绝测试命令，以及既有 editing/window-ui/perf 调用协议。涉及真实系统环境的验证另按项目授权规则处理。

## 2. 长期收益最大的业务重构：滚动状态收敛

### 代码证据

- `src/editorcommandregistry.cpp:2286` 的 `beginInputAutoScrollTracking()` 从 C++ 读取和设置 QML 的 hold 属性，并调用 QML 的准备入口。
- `checkInputAutoScroll()`（2341 行）管理布局后检查、触边目标、内容收缩保持和动画后的诊断采样。
- `qml/Main.qml:310` 起维护 hold、查找定位、跟随抑制、动画释放等状态；`prepareInputScrollTracking()`、`animateScrollTo()` 等函数也修改这些状态。
- `scrollTextDragViewport()`（命令注册实现 3449 行）直接改变视口位置；查找和标题导航另有取消及延迟定位逻辑。

### 为什么值得重构

同一滚动过程的生命周期跨越 C++ 和 QML，且多个行为修改同一组状态。代码已有新编辑打断旧动画、内容收缩前保持视口、布局稳定后复核等处理，说明交互复杂度来自真实业务，不能简单删除分支。

收益是让“谁拥有保持状态、谁能取消定位、何时释放动画保持”可以在明确边界内理解和验证，而不是减少几个属性或函数。

### 最小实施边界

先提取输入自动滚动这一垂直能力，明确开始跟踪、布局后检查、取消和释放保持的入口与状态归属。QML 继续负责视口和动画执行。后续再整理查找、标题导航、拖动与输入之间的优先关系。

不同业务的目标规则继续保留：输入触边的间歇式定位、方向键的最小跟随、查找定位和拖动边缘滚动不能硬合并成一种算法。不要一次搬走整个 TextEdit，也不要引入通用状态机框架。

### 验证重点

保留内容收缩首帧稳定性、动画中断、快速连续查找只保留最新目标、手动滚动取消旧定位、隐藏标题展开后定位、拖选越界滚动、动画关闭等回归。提取前后的可见行为必须相同。

## 3. 已存在规则分歧：Markdown 围栏识别

### 代码证据

- `src/cjktextprocessor.cpp:25` 的 `startsWithFenceOpener()` 支持反引号和波浪号，记录开启字符及长度；`isFenceCloser()` 检查长度和尾部内容。
- `src/headingfoldmanager.cpp:44` 的 `isFenceLine()` 只判断首个非空白位置是否至少有三个反引号，重建标题时遇到该行就切换围栏状态。
- `src/markdownhighlighter.cpp:431` 使用类似的三反引号布尔切换逻辑。
- `src/editorcommandregistry.cpp:5791` 的 `isInsideFencedBlock()` 使用 CJK 文档分析结果。

### 静态推导出的差异

| 输入场景 | CJK 保护区／编辑判断 | 标题折叠／高亮判断 |
|---|---|---|
| 波浪号围栏中出现标题 | 识别为围栏代码区域 | 当前围栏判断不识别波浪号，可能把内部标题当正文标题 |
| 四反引号开启后出现三反引号行 | 三反引号长度不足以关闭 | 简单切换逻辑会切换为围栏外 |
| 围栏内部出现带非空白尾部的反引号行 | 不满足关闭行检查 | 仍可能触发状态切换 |

这些差异尚未运行复现，也需要确认哪些语法属于产品期望支持范围，不能直接把某一实现视为最终规范。

### 最小实施边界

共享围栏行识别和状态推进的小型纯函数，各模块保留自己的扫描方式。不要引入完整 Markdown 解析树，不要让逐块高亮每次执行全文分析。

这项会改变可见行为，应作为一致性修复单独实施：先确认语法边界，再补能稳定暴露差异的检查，最后统一规则，不混入纯代码搬迁提交。

## 4. 第二梯队：列表变换算法提取

### 代码证据

`src/editorcommandregistry.cpp` 内集中定义了 `MarkdownListItem`、`parseMarkdownListItem()`（610 行）、`orderedListStructureAffected()`（1130 行）及编号修复相关逻辑。

路径插入、选区移动、外部文本插入、替换、删除、剪切、粘贴、列表 Enter 和缩进等入口均调用结构判断或 `repairOrderedLists()`。这些入口的触发策略有业务差异，不能机械去重。

### 最小实施边界与收益

优先提取给定文本和编辑范围后的列表识别、结构判断、编号修改计算；让算法能独立验证。事件顺序、文档写入、撤销分组及选区恢复继续留在命令协调层。

提取时保留 UTF-16 索引、倒序应用修改、单次全文读取／分析及线性复杂度约束。不要顺带改变编号策略，也不要将所有编辑包装进复杂事务框架。本文未对所有路径做复杂度证明，不宣称提取本身能提升运行性能。

## 5. 测试代码与暂不建议调整的部分

`tests/editing_main.cpp:435` 起的主入口承载多个编辑领域的验收。可按领域拆分函数和文件，复用 IPC 客户端和断言辅助，但保留可执行文件、脚本入口、独立 check 名、actual/expected 详情和产物格式。拆分前需确认用例间状态依赖，避免仅移动代码就改变执行语义。

暂不建议：

- 将命令表改为每个命令一个继承类，或引入插件式命令框架。
- 仅因 Main.qml 较长就全面拆组件；先处理滚动这一真实业务边界。
- 重写撤销系统；现有事务和反向选区语义敏感，不能为了统一形式改变行为。
- 进一步细分已有 coordinator/model/store/gateway 的剪贴板分层。
- 为已集中处理文件读写的 ExternalFileSession 增加仓储等额外抽象。

## 建议实施顺序与完成标准

1. 先隔离测试设施，保持所有对外协议和生产流程。
2. 完成对应隔离构建和回归后，再收敛输入滚动职责。
3. 随后评估拖动协调及列表纯文本算法提取。
4. 按既有维护路线整理 editing 验收代码。

围栏差异作为独立一致性问题处理，不与上述纯重构捆绑。实施优先级见[已确定的维护顺序](#已确定的维护顺序)。

每项重构应能够独立回退。完成标准是职责和状态所有权更清晰、既有边界行为保留且对应回归通过，而不是文件变短或类数量增加。实施时使用隔离 preset 和 `-SkipLocalInstall`；不自动部署稳定版本。
